## 2. Анализ предметной области

**АНО «Центр сохранения архитектуры»** выявляет и документирует объекты культурного наследия, систематизирует исторические материалы, сохраняет сведения об утраченных объектах и популяризирует наследие региона.

**Как турист узнаёт об объекте сейчас (AS-IS).** Сведения собираются из нескольких разрозненных источников:

| Источник | Что даёт | Недостаток |
|---|---|---|
| Поисковики, блоги, Википедия | историю объекта | сведения не проверены |
| PastVu, группы в соцсетях | старые фотографии | нет описания и контекста |
| Яндекс.Карты / 2ГИС | местоположение | утраченных объектов нет |
| Экскурсовод / турфирма | полный рассказ | по расписанию, за плату, фиксированный маршрут |
| Соцсети, блоги, форумы | возможность поделиться знаниями | публикуется без проверки |

### Выявленные проблемы (П1–П5)

- **П1. Разрозненность источников.** Описание объекта, старые фотографии и местоположение находятся в разных сервисах, объект приходится искать в каждом из них отдельно.
- **П2. Утраченные объекты не отображаются на картах.** Место снесённого здания турист определяет вручную по старому адресу и историческим названиям улиц.
- **П3. Нет готовых маршрутов для самостоятельного осмотра.** Тематические маршруты есть только у экскурсионных бюро — платно и по расписанию. Самостоятельно маршрут приходится составлять вручную (на AS-IS — блок «Составить маршрут вручную» и ветка с экскурсией).
- **П4. Сведения не проверены.** Сведения об объектах в интернете часто ничем не подтверждены (источник не указан, сайты пишут по-разному), и турист не может понять, чему верить; знания жителей и краеведов не попадают в проверенный источник (на AS-IS это показано веткой «поделиться в соцсетях без проверки»).
- **П5. У утраченных объектов нет панорамного вида.** Сохранившееся здание в окружении застройки можно увидеть хотя бы на месте, а утраченное — только на отдельных архивных снимках. Решение — панорамы, которые загружает модератор (платформа их не генерирует).

**Итог:** отсутствует единая точка доступа к достоверной информации об объектах историко-культурного наследия Астраханской области.

### Решения в TO-BE (Р1–Р4)

- **Р1 (→П1).** Единая карточка объекта: история, архивные фото, аудиогид, 3D-просмотр — в одном месте.
- **Р2 (→П2).** Утраченные объекты отмечены на карте по исходному адресу.
- **Р3 (→П3).** Готовые тематические маршруты и построение своего маршрута по объектам на карте; маршрут проходится с аудиогидом в любое время, без экскурсовода.
- **Р4 (→П1, П4).** Материалы проходят экспертную проверку и только после этого попадают в единую базу и на карту.

### Сравнение аналогов

| Критерий | PastVu | Яндекс.Карты | 2ГИС | Разрабатываемая платформа |
|---|---|---|---|---|
| Интерактивная 3D-реконструкция утраченных объектов | - | - | - | + |
| Просмотр исторической информации об объекте | +/- | - | - | + |
| Просмотр исторических фотографий | + | - | - | + |
| Модерация пользовательского контента | +/- | - | - | + |
| Формирование тематических туристических маршрутов | - | +/- | +/- | + |
| Централизованное хранение исторических материалов | +/- | - | - | + |
| Аудиогид с автоматическим сопровождением маршрута | - | - | - | + |

### Цель и задачи ВКР

**Цель:** повышение доступности и достоверности сведений об объектах историко-культурного наследия Астраханской области, в том числе утраченных, и сокращение времени на их поиск за счёт создания интерактивной веб-платформы. (Цель сформулирована как изменение ситуации, а разработка платформы — средство.)

**Задачи:**
1. Провести анализ предметной области, деятельности АНО и существующих аналогов.
2. Построить модели бизнес-процессов AS-IS и TO-BE, выявить проблемы текущего процесса.
3. Сформировать требования и построить диаграмму вариантов использования.
4. Спроектировать инфологическую модель данных и архитектуру платформы.
5. Реализовать веб-платформу: интерактивную карту, карточки объектов, маршруты, модерацию заявок и магазин.
6. Провести тестирование разработанной платформы.

## 3. Модели бизнес-процессов (BPMN 2.0)

Оформление: классическое чёрно-белое; в презентации проблемы выделены красным, решения — зелёным.

### AS-IS — один пул «Турист» + внешние пулы

Внешние пулы: Поисковики/блоги/Википедия, PastVu/группы в соцсетях, Яндекс.Карты/2ГИС, Соцсети/блоги/форумы, Экскурсовод/турфирма (обмен через потоки сообщений).

Ход процесса:
1. Возник интерес к объекту → «Выбрать способ знакомства с объектом» → ИЛИ-шлюз «Способ?».
2. **Без гида:** «Найти описание и старые фотографии объекта» (поисковики + PastVu) → «Найти местоположение объекта на карте» → шлюз «Объект есть на карте?»: нет → «Определить место по старому адресу вручную»; да → сразу к «Составить маршрут вручную».
3. **С экскурсией:** «Найти экскурсионную программу» → «Связаться с гидом и забронировать» → шлюз «Есть экскурсия на удобное время?»: нет → конец «Экскурсия недоступна»; да → «Пройти экскурсию по маршруту гида».
4. Слияние ветвей → «Посетить объекты» → шлюз «Хочет поделиться своими знаниями?»: нет → «Объекты посещены»; да → «Опубликовать свои сведения в соцсети или блоге» → конец «Сведения опубликованы без проверки».

Проблемные элементы, привязанные аннотациями: П1 — группа «найти описание + местоположение»; П2 — «Определить место вручную»; П3 — задачи с гидом; П4 — публикация без проверки.

Принятые решения по итогам обсуждения: без повторного поиска и петель; 3D и шеринг в соцсети сами по себе проблемами не считаются; П4 — именно непроверенная информация, которую публикуют пользователи.

### TO-BE — один пул «Веб-платформа исторического наследия Астраханской области», 4 дорожки

- **Турист (гость):** открыть платформу → «Способ знакомства?» (готовый тематический маршрут / свои объекты на карте с поиском и фильтрами) → изучить карточку (история, архивные фото, 3D) → пройти маршрут с аудиогидом → «Хочет поделиться своим объектом?».
- **Автор материала:** заполнить заявку (место, дата, источник, фото) → «Автор получил решение».
- **Веб-платформа (система):** показать объекты на карте, включая утраченные; построить маршрут и карточки; зарегистрировать заявку (статус «На модерации»); опубликовать объект на карте; уведомить автора о решении. Хранилище данных — «Единый реестр объектов наследия».
- **Модератор / эксперт АНО:** проверить достоверность, источник и дубликаты → «Решение по заявке?»: одобрить (→ публикация) / отклонить → указать причину отказа (→ уведомление автора).

**Почему TO-BE больше AS-IS** (вопрос на защите): в AS-IS показан только турист, потому что сейчас никакой системы нет. В TO-BE появляются новые участники и функции: система, автор материала и модератор, а также цикл проверки сведений — это и есть решение П4.

## 4. Диаграмма вариантов использования (UML Use Case)

Актёры и обобщение: **Гость ← Пользователь ← Модератор ← Администратор** (каждый следующий наследует возможности предыдущего).

**Гость:** просмотреть карту объектов (в т.ч. утраченных); искать и фильтровать объекты; просмотреть карточку объекта (extend: посмотреть 3D-модель, прослушать аудиогид); выбрать готовый маршрут; построить свой маршрут; просмотреть каталог товаров; зарегистрироваться.

**Пользователь:** авторизоваться; подать заявку на добавление объекта (extend: прикрепить фотографии; include: указать место, дату и источник); предложить фото или сведения к объекту (include: указать место, дату и источник); отслеживать статус заявки; сохранить маршрут; управлять корзиной (extend: добавить/удалить товар); оформить заказ (include: оплатить заказ); отслеживать статус заказа.

**Модератор:** просмотреть очередь заявок; одобрить заявку (include: уведомить автора); отклонить заявку (include: уведомить автора, указать причину отказа; extend: заблокировать пользователя); редактировать объект.

**Администратор:** управлять пользователями и ролями (extend: назначить/снять роль модератора); управлять категориями (extend: создать, изменить/удалить); управлять тематическими маршрутами (extend: изменить/удалить, создать; «создать» include «выбрать объекты и порядок посещения», extend «прикрепить аудиогид»); управлять товарами (extend: добавить, изменить/удалить); изменить статус заказа.

## 5. Архитектура (диаграмма развёртывания)

**Монолитная архитектура:** одно серверное приложение на Go, разделённое на модули, в Docker Compose на одном сервере (VPS, Linux). Сначала проектировались микросервисы, но от них отказались: при одном сервере и одной базе данных они не дают отказоустойчивости (если остановится PostgreSQL, остановится всё) и только усложняют разработку и сопровождение.

**Клиент:** устройство пользователя (ПК / смартфон) → веб-браузер → клиентская часть Next.js (карта Leaflet).

**Внешние системы:**
- OpenStreetMap — подложка (тайлы) карты, браузер загружает её напрямую по HTTPS;
- ЮKassa API — оплата заказов (HTTPS из приложения + уведомление об оплате, webhook);
- SMTP-сервер — отправка email (SMTP :587).

**Сервер (Docker Compose):**
- **nginx :443** — обратный прокси, TLS, маршрутизация: страницы → frontend, `/api` → backend, `/osrm` → OSRM.
- **frontend :3000** — Next.js-приложение (SSR).
- **backend :8080** — приложение на Go (монолит), REST API, модули:

| Модуль | Что делает |
|---|---|
| Авторизация | регистрация и вход, JWT, роли и права, блокировка пользователей |
| Каталог и маршруты | объекты и категории, тематические маршруты, геопоиск (PostGIS) |
| Заявки и модерация | приём заявок, проверка, решение по заявке |
| Медиафайлы | загрузка фото, 3D-моделей и аудио в MinIO, превью, ссылки |
| Магазин и оплата | товары, корзина, заказы, оплата через ЮKassa |
| Уведомления | фоновая отправка email через очередь задач в БД (с повторной попыткой) |

- **OSRM :5000** — свой экземпляр сервиса маршрутизации с графом пешеходных маршрутов по данным OSM (Южный федеральный округ / Астраханская область). Готовые тематические маршруты backend строит один раз и сохраняет линию в PostGIS; свой маршрут туриста браузер запрашивает через nginx (`/osrm`). Данные OSM периодически обновляются и граф пересобирается.
- **PostgreSQL 16 + PostGIS :5432** — одна база данных (на диаграмме — «БД»).
- **MinIO :9000** — бакеты: фото, 3D, аудио, изображения товаров.
- Тома Docker: `pg-data` и `minio-data`; ежедневное резервное копирование базы и файлов.

**Обоснование решений** (на случай вопросов):
- **Монолит, а не микросервисы:** небольшая нагрузка, один сервер и одна БД — монолит проще в разработке, тестировании и развёртывании; модульная структура позволяет при необходимости вынести модуль в отдельный сервис, а при росте нагрузки — запустить несколько экземпляров приложения за nginx.
- **Go:** быстрое и экономное приложение в одном исполняемом файле, удобно для REST API и фоновых задач, есть библиотеки для PostgreSQL/PostGIS, S3 (MinIO), JWT.
- **Уведомления без брокера сообщений:** задача на отправку письма ставится в очередь в БД, фоновый обработчик отправляет письмо — модератор не ждёт, при недоступности почтового сервера отправка повторяется.
- **OSRM на своём сервере:** бесплатно, открытый код, данные OSM, нет лимитов; публичный демо-сервер не используется — он без гарантий.
- **Отдельное хранилище файлов (MinIO):** фото, 3D и аудио хранятся не в БД, а в объектном хранилище.
- **Тома (volumes):** данные PostgreSQL и MinIO сохраняются при пересоздании контейнеров.

## 6. Модели данных

### Инфологическая модель (13 сущностей)

Роль, Пользователь, Заявка, Решение модерации, Медиафайл, Объект наследия, Категория, Точка маршрута, Маршрут, Заказ, Позиция заказа, Товар, Позиция корзины.

Основные связи: роль имеет пользователей; пользователь подаёт заявки, принимает решения модерации, сохраняет маршруты, оформляет заказы и добавляет товары в корзину; заявка дополняет объект и получает решение; медиафайлы прикреплены к заявке или иллюстрируют объект; категория включает объекты; маршрут состоит из точек, точка ссылается на объект; заказ содержит позиции, позиция ссылается на товар.

### Онтологическая модель

Чем отличается от инфологической: онтологическая описывает **понятия предметной области и смысловые отношения** между ними, а инфологическая — **данные, которые хранит система**.

Понятия: Объект наследия → Здание или сооружение (Культовое сооружение → Храм, Мечеть; Общественное здание), Памятник/монумент, Памятное место; Архитектор, Архитектурный стиль, Исторический период, Историческое событие, Историческая личность, Район города, Улица, Материал об объекте (Историческое фото, Архивный документ, Аудиогид), Источник сведений, Тематический маршрут.

Отношения: «находится в», «выполнен в стиле», «относится к», «произошло в», «принадлежал», «описывает», «подтверждается», «включает».

## 8. История основных правок (кратко)

- BPMN: проблемы сделаны конкретными; убраны повторный поиск, петли, красные/зелёные цвета на самих файлах; добавлена П4 (непроверенные сведения); в TO-BE без лишней петли — сразу уведомление автора.
- Use Case: перенесён в draw.io; добавлены include/extend, управление ролями, блокировка пользователей модератором, корзина, заказы и оплата.
- Развёртывание: прямые линии с протоколом на каждой связи; русские названия сервисов; одна БД со схемами; добавлены внешние системы; геокодер убран, OSRM подключается из браузера; итоговая компоновка — вертикальная.
- Презентация: простое оформление по шаблону практики; диаграммы перерисованы фигурами; шрифты на AS-IS, TO-BE и Use Case увеличены; добавлены слайд «Актуальность» и заметки докладчика; на диаграмме развёртывания БД подписана просто «БД».
- Архитектура: от микросервисов (6 сервисов, gRPC, RabbitMQ, API-шлюз) отказались в пользу монолита на Go с модулями; OSRM — свой экземпляр в Docker; диаграмма развёртывания, задача 4, текст защиты и «Вопросы к защите» обновлены.
- Презентация: слайд «Анализ предметной области» переделан (без статистических данных и без сравнения сервисов: схема разрозненности сведений об объекте и ключевая проблема про отсутствие единой карты с панорамами); добавлено синее акцентное оформление.
